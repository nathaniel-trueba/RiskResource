# 4. Reliability and monitoring

## Know when it's down

- **Uptime checks.** A free monitor (UptimeRobot, Better Stack, or a Route 53 health check) hitting `https://<backend>/api/health` and the homepage every few minutes, alerting by email or Slack.
- **Make `/api/health` meaningful.** Today it always returns `"status": "ok"`. Have it return a non-200 when the reference data isn't loaded, or report `degraded` when NWS is down and the archive fallback is in use (`nwsArchiveAsOf` is set) or the wildfire scores are stale (`wildfireModel.available` is false). Then the uptime monitor catches partial failures too.
- **Alarms on the scheduled jobs.** A CloudWatch alarm on Lambda errors (the alert archiver raises on failure, so errors are visible), and on the wildfire job (02).

## Logs

- The backend logs to stdout. Most hosts keep only a few days. Send logs somewhere searchable (Better Stack, Axiom, or CloudWatch if it's on AWS) with a 30-day retention.
- **Structured logs.** JSON lines with a request ID, the endpoint and the latency, so "why was the county page slow at 3 pm" has an answer.
- **CloudWatch log retention** for every Lambda log group: 30 days (`aws logs put-retention-policy --retention-in-days 30`). Never-expire is the default.

## Caching and scaling

- **The cache is per process.** Running more than one uvicorn worker, or more than one instance, multiplies every upstream call and makes instances disagree. Options, in order of effort:
  1. Stay on one worker. It's async, and one process handles a lot of traffic for this app.
  2. Put live feeds in a shared cache (Redis, such as Upstash's free tier) with the same TTLs.
  3. Move nationwide feeds out of the request path entirely: a scheduled job writes the snapshot every minute, and every instance reads it.
- **Startup depends on Supabase.** If the database is unreachable at startup, the API doesn't start. Keep a copy of the reference data with the deployment (`data/reference.json` already is one) and fall back to it, so a database outage degrades instead of breaking.

## Upstream budgets

All visitors share the backend's free upstream limits.

| Upstream | Limit | Today's protection | Improvement |
|---|---|---|---|
| NWS | Unpublished; needs a User-Agent | 5-minute cache, archive fallback | Fine |
| Open-Meteo | 10,000 calls/day, 600/min | 30-minute cache per county | Count calls per day, and stop per-county forecasts before the limit rather than after. The wildfire job shares this budget |
| NWPS | Unpublished; rate-limited us in testing | 15-minute cache, 5-minute backoff on 429 | Fine for demo traffic. A spike of different counties could still trip it |
| NASA POWER | ~100/min before 429 | Weekly job paces at 60/min | See 02 |

**Rate-limit our own API.** There's nothing stopping a script from requesting all 3,221 counties in a loop, which would spend the Open-Meteo and NWPS budgets for everyone. Add a per-IP limit (for example `slowapi`) on `/counties/{fips}`.

## When the whole site is down

The alert fallback helps when NWS is down, not when we are. If keeping people informed during our own outage matters:

- A static status page (Better Stack and Instatus have free ones) linked from the footer.
- Or a static "latest alerts" page regenerated by the Lambda into S3 or Vercel every 15 minutes, which keeps working even if the API and database are down.

## Timeouts and failure behaviour

- Upstream calls already time out at 15 seconds and degrade cleanly. The archive fallback adds a database connection with a 10-second timeout, but only during NWS outages.
- The frontend has no retry button and can't tell an outage from "no results" in map search. Add a retry, and distinguish errors from empty results.
